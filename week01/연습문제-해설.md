# 1주차 연습문제 해설

제출용이 아니다. 스스로 풀고 대조하는 용도이며, 중간고사 출제 범위가 이 문제들에서 나온다.

---

## 1번

> 문제: 같은 격리 네트워크에 VM을 한 대 더 배포하고, 두 VM이 사설 IP로 서로 ping이 되는지 확인하여 캡처를 제출하라. (Part E 13~14단계)

캡처 제출형이므로 정답 문장이 따로 없다. 아래 항목이 화면에 보이면 통과다.

### 통과 체크리스트

- 인스턴스 목록에 `web01-{학번}`, `web02-{학번}` 두 대가 모두 `Running` 이고, 둘의 네트워크 이름이 같다.
- 두 VM의 사설 IP 가 같은 `192.168.0.0/24` 안에 있다(관례상 `192.168.0.10`, `192.168.0.11`).
- 양방향 `ping` 이 모두 `0% packet loss` 다. 한쪽 방향만 찍은 캡처는 통과가 아니다.
- `ttl=64` 가 보인다. 중간에 라우터를 거치지 않았다는 근거다.
- `ip neigh` 에 상대 VM 이 `REACHABLE` 로 보인다.
- 프롬프트(`ubuntu@web01-{학번}`, `ubuntu@web02-{학번}`)가 캡처에 함께 들어가 어느 쪽에서 실행한 것인지 구분된다.

web01 에서 실행한 결과는 아래 형태가 된다.

```
$ ping -c 3 192.168.0.11
PING 192.168.0.11 (192.168.0.11) 56(84) bytes of data.
64 bytes from 192.168.0.11: icmp_seq=1 ttl=64 time=0.512 ms
64 bytes from 192.168.0.11: icmp_seq=2 ttl=64 time=0.446 ms
64 bytes from 192.168.0.11: icmp_seq=3 ttl=64 time=0.489 ms

--- 192.168.0.11 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms

$ ip neigh
192.168.0.11 dev ens3 lladdr 02:00:5c:1a:00:11 REACHABLE
192.168.0.1 dev ens3 lladdr 02:00:5c:1a:00:01 REACHABLE
```

두 VM 은 같은 서브넷에 있으므로 이 통신은 가상 라우터를 거치지 않는다. `ip route` 의 두 번째 줄 `192.168.0.0/24 dev ens3 proto kernel scope link` 가 그 근거다. 3주차 Keepalived(VRRP)가 이 직접 통신을 전제로 동작한다.

### 흔한 오답

- ICMP Egress 규칙을 지운 상태에서 실패한 것을 두고 "사설망이 안 된다"고 적는 경우다. Egress 는 격리 네트워크 밖으로 나가는 트래픽만 통제하므로, 같은 `/24` 안의 `ping` 에는 영향이 없다.
- web02 를 다른 네트워크에 배포한 경우다. 두 VM 의 `ip -4 addr show ens3` 결과가 같은 `/24` 인지 먼저 비교한다.
- 노트북에서 `ping 192.168.0.11` 을 시도한 캡처를 내는 경우다. VPN 은 `192.168.0.0/24` 로 직접 라우팅되지 않으므로 실패가 정상이며, 이 문제는 VM 안에서 실행해야 한다.

## 2번

> 문제: 방화벽에서 SSH(2201) 외의 포트는 모두 닫힌 상태를 유지해야 하는 이유를, 정보보안 관점(공격 표면)에서 3~4문장으로 서술하라.

### 채점 기준

- "공격 표면"을 열린 포트 수 및 출처 범위와 연결해 설명했는가.
- 필요한 최소한만 여는 원칙(최소 권한 · 기본 차단)을 언급했는가.
- 이번 실습의 실제 값(TCP 2201, Source CIDR `10.8.0.0/24`)을 근거로 들었는가.
- 열린 포트가 늘어나면 관리 부담(패치 · 로그 · 인증 강도 점검)도 함께 늘어난다는 점을 짚었는가.

### 정답 예시

방화벽에서 열린 포트 하나하나는 외부에서 시도할 수 있는 진입점이 되므로, 열린 포트와 허용 출처의 넓이가 곧 공격 표면의 크기다. 이번 실습에서 필요한 것은 SSH 한 가지뿐이므로 TCP 2201 만 열고 나머지를 닫아 두면, 다른 포트에서 취약한 서비스가 떠 있어도 외부에서는 시도조차 할 수 없다. 여기에 Source CIDR 을 VPN 대역 `10.8.0.0/24` 로 한정했으므로, 인증을 시도할 수 있는 대상 자체가 VPN 에 들어온 사용자로 줄어든다. 열린 포트는 그 서비스의 패치 · 인증 설정 · 접속 로그를 계속 관리해야 하는 대상이 되기도 하므로, 필요할 때 열고 끝나면 닫는 것이 운영 비용까지 함께 줄이는 방법이다.

### 흔한 오답

- "보안상 위험하니까 닫는다"로 끝내는 답이다. 무엇이 왜 위험해지는지(진입점 증가, 출처 무제한)를 적어야 점수가 된다.
- 게스트 OS 방화벽(`ufw`)과 CloudStack 방화벽을 섞어 쓰는 답이다. 이 문제는 공용 IP 앞단, 즉 가상 라우터의 방화벽 규칙을 말한다.
- Source CIDR 을 `0.0.0.0/0` 으로 열어도 비밀번호가 있으니 괜찮다고 쓰는 답이다. 이 환경의 초기 비밀번호는 `ubuntu` / `ubuntu` 이므로 출처 제한이 사실상 유일한 방어선이다.

## 3번

> 문제: Egress 규칙에서 목적지를 제한하지 않는 것이 운영 환경에서 왜 위험한지 설명하고, 대안을 한 가지 제시하라.

### 채점 기준

- 위험을 아웃바운드 방향의 문제로 정확히 짚었는가(침해 이후의 외부 통신, 데이터 유출, 외부 명령 수신).
- 이번 실습의 실제 설정을 근거로 들었는가(포트는 UDP 53 · TCP 80 · TCP 443 · ICMP 네 줄로 좁혔고 목적지는 열어 둠).
- 대안을 한 가지 이상 구체적으로 제시했는가(목적지 CIDR 한정, 저장소 미러 · 프록시 경유 등).
- 대안의 비용이나 한계를 함께 언급했는가(주소 변동, 목록 유지 부담).

### 정답 예시

목적지를 제한하지 않으면 허용한 포트로는 어디로든 나갈 수 있다. 이번 실습은 UDP 53 · TCP 80 · TCP 443 · ICMP 네 줄만 허용했지만 목적지가 비어 있으므로, VM 이 한 번 침해되면 공격자는 같은 443 포트로 임의의 외부 서버에 접속해 명령을 받거나 내부 데이터를 밖으로 내보낼 수 있다. 인바운드 방화벽은 이 통신을 막지 못한다. 나가는 연결은 VM 이 스스로 시작하고 응답만 되돌아오는 형태라서, 인바운드 규칙 관점에서는 정상 트래픽과 구분되지 않는다.

대안은 Egress 규칙의 Destination CIDR 을 실제로 필요한 목적지로 좁히는 것이다. 예를 들어 패키지 저장소와 이름 서버 대역만 지정하고, 그 외 목적지는 허용하지 않는다. 다만 저장소 주소는 미러에 따라 바뀔 수 있어 목록 유지 부담이 생기므로, 실무에서는 사내 저장소 미러나 프록시 서버 한 곳만 목적지로 허용하고 VM 은 그곳만 바라보게 하는 방식을 함께 쓴다. 7주차에서 이 실습의 Egress 를 목적지까지 좁힌 최소 허용으로 바꾼다.

### 흔한 오답

- "외부에서 침입할 수 있어 위험하다"고 쓰는 답이다. Egress 는 아웃바운드 전용이므로 인바운드 침입과는 방향이 다르다.
- 대안으로 "Egress 규칙을 전부 지운다"를 제시하는 답이다. 그러면 `apt` 도 동작하지 않아 실습 자체가 불가능하며, 최소 허용이 아니라 전면 차단이다.
- 대안으로 "포트를 더 좁힌다"만 쓰는 답이다. 포트는 이미 네 줄로 좁힌 상태이며, 문제가 요구한 것은 목적지 축소다.

## 4번

> 문제: 포트포워딩과 방화벽이 왜 둘 다 필요한가. 8단계만 하고 9단계를 하지 않았을 때, 그리고 9단계만 하고 8단계를 하지 않았을 때 각각 `nc -vz` 결과가 어떻게 다른지 예측하고, 그 이유를 설명하라. (실제로 규칙 하나를 잠시 지워 확인한 뒤 원복해도 된다)

### 채점 기준

- 두 규칙의 역할을 구분해 서술했는가(포트포워딩은 "어디로 전달할지", 방화벽은 "들여보낼지 말지").
- 두 경우의 실패 양상을 다르게 예측했는가(조용히 버려짐 대 즉시 거절).
- 실패 메시지의 차이를 진단 근거로 쓸 수 있다고 설명했는가.
- 두 규칙이 가상 라우터의 서로 다른 처리 단계에 있다는 점을 짚었는가.

### 정답 예시

포트포워딩은 공용 IP 의 2201 번으로 들어온 요청을 `192.168.0.10` 의 22 번으로 바꿔 전달하라는 규칙이고, 방화벽은 그 요청을 애초에 들여보낼지 말지를 출처 CIDR 과 포트로 판정하는 규칙이다. 두 규칙은 가상 라우터에서 서로 다른 단계를 담당하므로 하나만 있으면 접속이 되지 않는다.

8단계만 하고 9단계를 하지 않으면, 전달할 대상은 정해졌지만 요청이 방화벽에서 걸러진다. 이때 패킷은 응답 없이 버려지므로 클라이언트는 답을 받지 못하고 기다리다 끝난다.

```
$ nc -vz {{공용IP}} 2201
nc: connectx to 203.0.113.10 port 2201 (tcp) failed: Operation timed out
```

9단계만 하고 8단계를 하지 않으면, 요청은 가상 라우터까지 들어오지만 2201 번을 전달할 대상이 없다. 받아 줄 것이 없다는 응답이 즉시 돌아오므로 타임아웃 없이 바로 끊긴다.

```
$ nc -vz {{공용IP}} 2201
nc: connectx to 203.0.113.10 port 2201 (tcp) failed: Connection refused
```

정리하면 `Operation timed out` 은 경로가 막힌 것이고(방화벽 · VPN 을 본다), `Connection refused` 는 경로는 뚫렸으나 대상이 없는 것이다(포트포워딩의 대상 인스턴스와 사설 포트를 본다). 두 메시지의 차이가 어느 규칙을 고쳐야 하는지 알려 주는 신호이므로, 접속 실패 때 메시지를 먼저 읽는 습관이 진단 시간을 줄인다. 응답을 돌려주지 않는 구간이 앞에 하나 더 있으면 두 경우가 모두 타임아웃으로 보일 수 있으므로, 판정은 메시지 하나만 보지 않고 규칙 목록을 함께 확인해 내린다.

### 흔한 오답

- 두 경우를 모두 "접속 안 됨"으로만 쓰는 답이다. 문제가 요구한 것은 실패 양상의 차이와 그 이유다.
- Egress 규칙을 원인으로 드는 답이다. SSH 인바운드 경로에 Egress 는 관여하지 않는다.
- 방화벽만 열면 `sshd` 에 붙는다고 예측하는 답이다. VM 은 사설 IP 만 가지고 있어 포트포워딩 없이는 바깥에서 지목할 수 없다.

## 5번

> 문제: 경로 그리기. 이 문서의 아키텍처 도식을 보지 않고, 내 노트북에서 `ssh -p 2201`을 입력한 순간부터 web01의 `sshd`에 도달할 때까지 패킷이 거치는 구간을 순서대로 쓰고, 각 구간에서 통과 여부를 결정하는 설정 이름을 적어라.

### 채점 기준

- 구간을 순서대로 빠짐없이 나열했는가(노트북 → VPN → 교내망 → 가상 라우터 → 격리 네트워크 → web01).
- 각 구간마다 통과 여부를 결정하는 설정 이름을 짝지었는가.
- 가상 라우터 안에서 방화벽 판정과 포트포워딩 변환을 두 단계로 구분했는가.
- Egress 가 이 경로에 관여하지 않는다는 점을 알고 있는가(적으면 가점, 경로에 넣으면 감점).

### 정답 예시

| 순서 | 구간 | 통과 여부를 결정하는 설정 |
| --- | --- | --- |
| 1 | 내 노트북의 `ssh` 클라이언트가 공용 IP 의 2201 번으로 TCP 연결을 시작한다 | 목적지 포트 지정(`-p 2201`), 노트북의 로컬 방화벽 |
| 2 | 패킷이 VPN 터널로 들어가 교내망으로 나간다 | VPN 연결 상태. 연결되어 있어야 교내망 주소로 라우팅된다 |
| 3 | 교내망에서 가상 라우터의 공용 IP 에 도달한다 | 그 네트워크에 할당된 Source NAT 공용 IP 의 존재 |
| 4 | 가상 라우터가 인바운드 판정을 한다 | 방화벽 규칙(Source CIDR `10.8.0.0/24`, TCP 2201) |
| 5 | 가상 라우터가 목적지를 바꿔 전달한다 | 포트포워딩 규칙(Public port 2201, Private port 22, 대상 인스턴스 web01) |
| 6 | 격리 네트워크 `192.168.0.0/24` 안에서 web01 의 `ens3` 로 전달된다 | VM 이 그 네트워크에 붙어 있고 상태가 `Running` 인지, 사설 IP 가 규칙의 대상과 일치하는지 |
| 7 | web01 게스트 OS 안에서 22 번으로 들어간다 | 게스트 OS 방화벽(`ufw`, 기본 `inactive`) |
| 8 | `sshd` 가 연결을 받고 인증한다 | `sshd` 서비스 상태(`active (running)`), 계정 `ubuntu` 의 비밀번호 또는 `~/.ssh/authorized_keys` |

4번과 5번이 가상 라우터 한 대 안에서 일어나지만 서로 다른 판정이라는 것이 이 문제의 핵심이다. 4번에서 막히면 응답이 없어 타임아웃이고, 5번의 대상이 잘못되어 있으면 거절 응답이 돌아온다. 7번과 8번은 네트워크가 아니라 서버 안의 문제이므로, 여기가 원인일 때는 콘솔의 `View Console`(VNC)로 들어가 확인한다. VNC 는 4번과 5번을 거치지 않으므로 규칙이 어떻게 되어 있어도 동작한다.

경로 확인에 쓰는 명령은 다음과 같다.

```
# 내 노트북에서: 3~5번 구간까지 뚫렸는지 본다
nc -vz {{공용IP}} 2201

# web01 안에서: 6~8번 구간을 본다
ip -4 addr show ens3
ip route
ss -tlnp
```

```
$ ip route
default via 192.168.0.1 dev ens3 proto dhcp src 192.168.0.10 metric 100
192.168.0.0/24 dev ens3 proto kernel scope link src 192.168.0.10 metric 100
```

`default via 192.168.0.1` 의 `192.168.0.1` 이 4번과 5번을 처리한 가상 라우터와 같은 장비다. 콘솔에서 입력한 게이트웨이 주소가 서버 안 라우팅 테이블에 그대로 나타난 것이다.

### 흔한 오답

- Egress 규칙을 경로 중간에 넣는 답이다. Egress 는 VM 이 바깥으로 나갈 때만 판정하므로 SSH 인바운드에는 관여하지 않는다.
- VPN 이 `192.168.0.0/24` 까지 연결해 준다고 쓰는 답이다. VPN 은 교내망까지만 연결하고 격리 네트워크 안쪽으로는 직접 라우팅되지 않으므로, 4번과 5번을 거치는 것이 유일한 경로다.
- 방화벽과 포트포워딩을 한 줄로 합쳐 쓰는 답이다. 두 구간을 구분하지 못하면 4번 문제도 함께 틀린다.

## 6번

> 문제: 9주차 미리 보기. 오늘 콘솔에서 만든 자원(네트워크 1개, VM 1~2대, Egress 규칙 4줄, 포트포워딩 1~2개, 방화벽 1~2개)의 개수를 세고, 이 중 사람이 실수하기 쉬운 항목이 무엇이며 왜 그런지 2~3문장으로 서술하라. 9주차에는 이것을 Terraform 코드로 만든다.

### 채점 기준

- 개수를 실제로 세어 합계를 냈는가(Part E 를 했는지에 따라 8개 또는 11개).
- 실수하기 쉬운 항목을 하나 이상 지목하고 이유를 붙였는가.
- 이유가 "손으로 값을 입력한다"는 성질과 연결되는가(화면마다 흩어진 입력란, 확인 지점의 부재).
- 자동화가 이 문제를 어떻게 줄이는지 한마디라도 언급했는가.

### 정답 예시 (개수)

| 자원 | 필수 구간까지 | Part E 까지 |
| --- | --- | --- |
| 격리 네트워크 | 1 | 1 |
| VM | 1 | 2 |
| Egress 규칙 | 4 | 4 |
| 포트포워딩 규칙 | 1 | 2 |
| 방화벽 규칙 | 1 | 2 |
| 합계 | 8 | 11 |

여기에 가상 라우터와 공용 IP 는 직접 만들지 않았는데도 생겼다. 첫 VM 이 배포될 때 CloudStack 이 자동으로 기동하고 Source NAT 공용 IP 하나를 할당하기 때문이다. 세는 대상은 "내가 클릭해서 만든 것"이고, 이 두 가지는 그 결과로 딸려 온 것이다.

### 정답 예시 (서술)

필수 구간까지 8개, Part E 까지 하면 11개를 손으로 만들었다. 이 중 가장 실수하기 쉬운 것은 방화벽의 Source CIDR 과 포트포워딩의 공용 포트 · 사설 포트 짝이다. 두 값 모두 화면에서 자유 입력이라 `10.8.0.0/24` 를 `10.8.1.0/24` 로 잘못 넣거나 2201 과 22 를 뒤집어도 콘솔은 그대로 저장하고, 잘못됐다는 사실은 접속 실패라는 간접 증상으로만 드러나기 때문이다. Egress 4줄 중 UDP 53 한 줄을 빠뜨리는 것도 흔한데, 이 경우 `ping` 은 되는데 `apt` 만 안 되는 식으로 증상이 갈려 원인을 찾기 어렵다. 9주차에 이 11개를 Terraform 코드로 옮기면 값이 파일 한 곳에 적히고 `terraform plan` 으로 적용 전에 확인할 수 있으므로, 같은 구성을 다시 만들 때 이런 입력 실수가 반복되지 않는다.

### 흔한 오답

- 가상 라우터와 공용 IP 를 "내가 만든 자원"으로 세는 답이다. 이 둘은 자동으로 만들어진 것이므로 구분해 적는다.
- 실수하기 쉬운 항목으로 "VM 이름"만 드는 답이다. 이름은 틀려도 즉시 눈에 보이므로, 잘못된 상태가 조용히 유지되는 값(출처 CIDR, 포트 짝, 대상 인스턴스)을 지목하는 것이 요지에 맞다.
- 정리(Destroy)할 때 `expunge` 를 켜지 않아 볼륨이 남는 것도 같은 성질의 실수다. 답안에 넣으면 가점 요소가 된다.
