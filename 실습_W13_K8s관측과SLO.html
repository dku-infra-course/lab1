도구 준비와 클러스터 확인 · 5분필수

11주차에서 이어 온 클러스터면 이 블록은 건너뛰어도 된다. Terraform으로 클러스터를 새로 만들었다면 노드에 kubectl과 helm이 없고 ~/.kube/config도 없으므로 먼저 실행한다. 이미 있는 도구는 건너뛰도록 되어 있어 다시 실행해도 안전하다.

command -v kubectl >/dev/null || { curl -LO "https://dl.k8s.io/release/v1.32.5/bin/linux/amd64/kubectl" && sudo install -m 0755 kubectl /usr/local/bin/kubectl; }
[ -f ~/.kube/config ] || { mkdir -p ~/.kube && sudo cp /etc/kubernetes/admin.conf ~/.kube/config && sudo chown $(id -u):$(id -g) ~/.kube/config && chmod 600 ~/.kube/config; }
command -v helm >/dev/null || { curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 && chmod 700 get_helm.sh && DESIRED_VERSION=v3.22.0 ./get_helm.sh; }

이어서 클러스터와 도구를 확인한다.

kubectl get nodes -o wide
helm version
kubectl get pods -A | grep -v Running | grep -v Completed

이번 실습 내내 쓸 노드 IP를 변수로 한 번만 정해 둔다(control 노드의 INTERNAL-IP). 새 SSH 접속에서도 쓰도록 ~/.bashrc에 저장한다.

export NODE_IP=$(kubectl get nodes -l node-role.kubernetes.io/control-plane -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
grep -q NODE_IP ~/.bashrc || echo "export NODE_IP=$NODE_IP" >> ~/.bashrc
echo "Grafana http://$NODE_IP:30030  Prometheus http://$NODE_IP:30090  Alertmanager http://$NODE_IP:30093  frontend http://$NODE_IP:30980"

마지막 줄에 나온 주소를 본인 PC 브라우저에 붙여 넣어 접속한다(VPN 연결 필요). 컨트롤 노드 안의 명령은 $NODE_IP를 그대로 쓰므로 다시 입력하지 않는다.

위 블록이나 11주차에서 설정한 ~/.kube/config를 쓴다. INTERNAL-IP가 NODE_IP이며 control 노드의 값을 쓴다(E2에서 worker를 멈춰도 접속 지점이 남는다). 컨트롤 노드 안에서도, 본인 PC 브라우저에서도 같은 값을 쓴다.

확인 기준 (읽는 기준이며 할 일이 아니다)
  • 노드 2대가 Ready이고 helm version이 3.x를 출력하며 echo $NODE_IP가 control 노드 IP를 출력하면 통과.
클러스터나 helm이 없을 때
  • 클러스터가 없으면 11주차의 terraform/w11-k8s/README.md로 먼저 만든다(본인 PC에서 Terraform 실행). 이 주차에는 클러스터 생성 코드가 없다.
  • worker 1대: E2에서 멈추면 서비스 전체가 멈춘다. 14주차에 2대로 늘려 비교한다.

알아 둘 개념

  • ServiceMonitor: "이 라벨의 Service를 이 포트로 긁어 가라"는 쿠버네티스 리소스(CRD)다. Prometheus 설정 파일을 직접 고치지 않고 YAML 하나로 수집 대상을 추가한다. 이 Prometheus가 고르려면 release: kps 라벨이 있어야 한다.
  • PrometheusRule: 기록 규칙(미리 계산)과 알림 규칙을 담은 리소스다. Part C에서 slo-rules.yaml로 적용한다.
  • Prometheus Operator: 위 리소스를 감시하다가 바뀌면 Prometheus에 반영하는 컨트롤러다. 그래서 kubectl apply만으로 설정이 바뀐다.

Part B: SLI와 SLO (필수 · 약 10분)

왜 필요한가

  • SLI는 잰 값, SLO는 목표다(13-1).
  • 가용성 = 성공 요청 수 / 전체 요청 수, 지연 = p95
  • 요청이 없으면 값이 비므로 먼저 요청을 보낸다.
B1

요청을 보내고 PromQL로 SLI 읽기 · 5분필수

for i in $(seq 1 100); do curl -s -o /dev/null http://$NODE_IP:30980/; done

본인 PC 브라우저에서 Prometheus(http://<NODE_IP>:30090, 0-2에서 출력한 주소) Graph 탭을 연다. 아래 식을 하나씩 입력창에 붙여 넣고 Execute를 누른다. 성공은 5xx가 아닌 요청이다. 위 curl 반복은 컨트롤 노드에서 실행한다.

식 1. 가용성(0.99 이상이면 SLO 충족). 첫 번째 입력창에 붙여 넣고 Execute를 누른다. Graph 탭으로 바꾸면 시간에 따른 선이 보인다.

sum(rate(http_requests_total{namespace="sre-lab",job="frontend-podinfo",status!~"5.."}[5m])) / sum(rate(http_requests_total{namespace="sre-lab",job="frontend-podinfo"}[5m]))

식 2. p95 지연(초 단위, 0.5 미만이면 SLO 충족). 화면 아래의 Add query를 눌러 새 입력창을 만든 뒤 붙여 넣고 Execute를 누른다. 한 입력창에는 식 하나만 넣는다.

histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{namespace="sre-lab",job="frontend-podinfo"}[5m])))

화면 예: 가용성(Graph 탭)은 값이 1.00으로 일정하고, p95(Table 탭)는 0.005 안팎이다. 화면 위쪽의 빈 입력창은 처음 열렸을 때의 기본 입력창이다.

확인 기준 (읽는 기준이며 할 일이 아니다)
  • 가용성이 1 근처이고 p95가 수 ms이면 통과. 값이 비면 요청을 다시 보낸다.
항목참고값(강사 실측)내 결과와 비교할 점
가용성(부하 없음, 100요청 직후)1 (100%)1보다 낮으면 5xx가 있다. 0 또는 값이 비면 요청이 없다.
p95 지연(부하 없음)5ms 이하 (가장 작은 구간 0.005초)수 ms에서 수십 ms면 정상 범위다. 0.5초에 가까우면 원인을 찾는다.

(강사 실측, Solid Cloud, 2026-11-22) 환경에 따라 달라지며, 내 결과가 크게 다르면 원인을 생각해 본다.

패널보는 법정상 범위

E2

S1 시나리오: worker VM 정지 · 10분필수

  • S1은 노드가 사라지는 장애다.
  • 가설: VM을 멈추면 서비스가 즉시 끊기고, 켜면 Pod가 올라오며 복구된다.
  • worker 1대라 앱과 관측 스택이 모두 멈춘다(SPOF).
  • 정지 중에는 Grafana가 안 보이므로 별도 터미널에서 컨트롤 노드에 SSH로 한 번 더 접속해 1초마다 잰다. 이 터미널의 mark.sh와 timeline.csv는 ~/lab1/week13-sre 안에 둔다.
while true; do echo "$(date -u +%FT%TZ) $(curl -s -m 2 -o /dev/null -w '%{http_code}' http://$NODE_IP:30980/healthz)"; sleep 1; done | tee e2-curl.log
  1. ./scripts/mark.sh 주입 "E2 worker stop" 후 콘솔 Instances에서 본인 클러스터(k8s-<학번>)의 worker VM을 Stop한다. kubectl get nodes의 worker 이름과 대조하고, control은 건드리지 않는다.
  2. curl이 처음 000이 되면 ./scripts/mark.sh 감지 "E2 curl fail".
  3. VM을 Start하고 ./scripts/mark.sh 완화 "E2 vm start".
  4. curl이 다시 200이 되면 ./scripts/mark.sh 복구 "E2 curl 200". kubectl get nodes도 본다.
  • 중단 시간 = 복구 시각 - 주입 시각 (또는 curl 로그의 000 구간)
  • 감지 지연 = 감지 시각 - 주입 시각
  • 복구 소요 = 복구 시각 - 완화 시각 (VM 시작 후)
  • 세 값은 timeline.csv와 e2-curl.log로 계산한다.
확인 기준 (읽는 기준이며 할 일이 아니다)
  • E2 4줄이 있고 e2-curl.log의 000 구간이 중단 시간과 맞으며 Pod가 Running이면 통과.

감지 지연(주입에서 curl 첫 000까지)약 6초정지 명령이 반영되는 시간이다. 길면 콘솔 반응이 느린 것이다.
복구 소요(VM 시작에서 curl 200까지)1분 15초 ~ 1분 50초Pod 재스케줄과 이미지 확인 시간이 포함된다.
