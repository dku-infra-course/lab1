# 2주차 연습문제 해설

제출용이 아니다. 스스로 풀고 대조하는 용도이며, 중간고사 출제 범위가 이 문제들에서 나온다.

## 1번

> 문제: **내 VM 스펙표 작성 + 이론 매핑.** `lscpu`·`free -h`·`df -h` 결과로 아래 표를 채우고, 이 VM이 이론의 어떤 서버 유형(범용/CPU/메모리/스토리지/GPU)에 가장 가까운지 한 문장으로 근거와 함께 서술하라.

네 값을 한 번에 뽑는 명령은 2-5단계의 것을 그대로 쓴다.

```
echo "== HOST ==";  hostname
echo "== OS   =="; grep PRETTY_NAME /etc/os-release; uname -r
echo "== CPU  =="; nproc; lscpu | grep -E 'Architecture|^CPU\(s\)'
echo "== MEM  =="; free -h | awk '/^Mem:/ {print "total="$2, "available="$7}'
echo "== DISK =="; df -h / | tail -1
```

아래 표는 컴퓨트 오퍼링 **Medium(2 CPU / 4096MB)** 로 배포한 경우의 예시값이다. **본인 값은 다를 수 있다.** 고른 오퍼링(Small 1/2048, Medium 2/4096, Large 4/8192, XLarge 8/16384)에 따라 vCPU와 메모리가 달라지고, 커널 버전 숫자는 템플릿 패치 시점에 따라 달라진다.

| 항목 | 확인 명령 | 내 VM 값 (예시) |
|---|---|---|
| vCPU 수 | `lscpu` / `nproc` | `2` (`Architecture: x86_64`, `CPU(s): 2`) |
| 메모리(RAM) | `free -h` | `total=3.8Gi available=3.3Gi` (오퍼링 표기 4096MB) |
| 디스크 용량/여유 | `df -h` | `/dev/vda1 19G`, 여유 `16G`, 사용률 약 `15%`, `Mounted on /` |
| OS/커널 | `uname -a` | `Ubuntu 24.04 LTS`, 커널 `6.8.0-xx-generic`, `x86_64` |

실제 출력은 이런 모양이다.

```
$ nproc
2

$ free -h
               total        used        free      shared  buff/cache   available
Mem:           3.8Gi       0.4Gi       2.9Gi       0.0Ki       0.6Gi       3.3Gi

$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        19G  2.7G   16G  15% /

$ uname -a
Linux web01-{학번} 6.8.0-xx-generic #xx-Ubuntu SMP ... x86_64 x86_64 x86_64 GNU/Linux
```

### 채점 기준

- 네 칸(vCPU / RAM / 디스크 / OS·커널)을 모두 **본인 출력의 값으로** 채웠다. 오퍼링 표기값을 그대로 옮겨 적은 것은 실측이 아니다.
- 디스크 칸에서 `Mounted on`이 `/`인 줄(`/dev/vda1`)을 골랐다. `tmpfs` 줄을 적으면 감점이다.
- 서버 유형을 **범용(General)** 으로 지목했다.
- 근거가 표의 값에서 나왔다. "vCPU와 RAM이 균형", "GPU 없음", "디스크가 20GB 급의 소형" 중 하나 이상을 값으로 제시했다.

### 정답 예시

vCPU 2개와 RAM 3.8Gi가 어느 한쪽으로 치우치지 않고, 루트 디스크도 19G의 소형이며 `lspci | grep -i vga`에 가속기가 잡히지 않으므로, 이 VM은 이론의 다섯 유형 중 CPU·메모리 균형형인 **범용(General)** 서버에 가장 가깝고 웹·API 서버 용도에 대응한다.

### 흔한 오답

- `df -h`의 첫 줄(`tmpfs`)을 디스크 용량으로 적는다. `tmpfs`는 메모리 기반 임시 영역이며 디스크가 아니다.
- 콘솔 오퍼링 표기의 `0.50 GHz`를 보고 "CPU 최적화가 아니다"의 근거로 클럭을 든다. 이 값은 CloudStack 오퍼링 정의값이고 실제 물리 클럭이 아니므로 판단 근거로 쓸 수 없다.

## 2번

> 문제: **자동시작 검증.** `sudo systemctl enable apache2`로 자동시작을 설정한 뒤 `sudo reboot`로 재부팅하고, 재접속 후 `systemctl status apache2`가 **별도 조작 없이** `active (running)`인지 캡처하여 제출하라. (재접속: `ssh ubuntu@{{VM_IP}}`)

캡처 제출형이므로 정답 문장이 아니라 **화면에 무엇이 보여야 통과인지**가 기준이다.

```
# 재부팅 전
sudo systemctl enable apache2
systemctl is-enabled apache2      # -> enabled
sudo reboot

# 재접속 후. start 를 치지 않는다
ssh ubuntu@10.0.X.X
uptime
systemctl status apache2 --no-pager
```

```
$ uptime
 09:31:07 up 1 min,  1 user,  load average: 0.31, 0.12, 0.04

$ systemctl status apache2 --no-pager
* apache2.service - The Apache HTTP Server
     Loaded: loaded (/usr/lib/systemd/system/apache2.service; enabled; preset: enabled)
     Active: active (running) since Mon 2026-08-24 09:30:11 UTC; 56s ago
   Main PID: 1102 (apache2)
```

### 통과 체크리스트

- [ ] 프롬프트에 `ubuntu@web01-{학번}`이 보인다. 본인 서버임을 알 수 있다.
- [ ] `Loaded:` 줄에 `enabled`가 있다. 자동시작이 설정된 상태다.
- [ ] `Active: active (running)`이다.
- [ ] `since ...; N초 전`(또는 `N분 전`)이며, 같은 화면의 `uptime`이 그와 비슷하게 짧다. 재부팅 직후에 스스로 올라왔다는 증거는 이 두 값이 맞아떨어지는 것이다.
- [ ] 캡처 안에 `systemctl start`를 실행한 흔적이 없다. 재접속 직후 바로 `status`를 찍은 화면이어야 한다.

### 흔한 오답

- 재부팅 후 접속해 `sudo systemctl start apache2`를 먼저 실행하고 그다음 `status`를 캡처한다. 이 화면은 자동시작을 증명하지 못한다.
- `enable`만 하고 재부팅을 하지 않는다. `since`가 몇 시간, 며칠 전으로 나오고 `uptime`도 길게 나오므로 바로 드러난다.
- 참고로 우분투 패키지는 `apt install apache2` 시점에 이미 `enable`과 `start`를 함께 수행한다. 설치 로그의 `Created symlink ...multi-user.target.wants...` 한 줄이 그것이다. 그래도 `is-enabled`로 직접 확인하는 것이 이 문제의 목적이다. 배포판·패키지마다 이 동작이 다르기 때문이다.

## 3번

> 문제: **오퍼링 vs 실측 비교.** VM 생성 시 고른 컴퓨트 오퍼링(스펙 표기값)과, 실제 `lscpu`·`free -h`·`df -h` 결과를 비교하라. 일치하는 항목과, 표기와 다르게 보이는 항목(예: RAM이 표기보다 조금 작게 나오는 이유 등)을 3~4문장으로 서술하라.

| 항목 | 오퍼링 표기값 | 실측값 (예시) | 차이의 이유 |
|---|---|---|---|
| vCPU | Medium 기준 `2 core` | `nproc` = `2` | 대개 정확히 일치한다 |
| 메모리 | Medium 기준 `4096MB` | `free -h` total `3.8Gi` | 커널·펌웨어가 예약한 영역이 total에서 빠진다. GB와 GiB의 단위 차이도 겹친다 |
| 디스크 | Root disk 기본 `20GB` | `df -h /`의 `19G`, `lsblk`의 `vda1` | 나머지 약 1G를 `/boot`·`/boot/efi` 등이 쓴다. 파일시스템 예약 블록도 있다 |

### 채점 기준

- vCPU는 표기와 실측이 일치한다는 점을 명시했다.
- 메모리가 표기보다 작게 나오는 이유로 **커널·펌웨어 예약 영역**과 **GB/GiB 단위 차이**를 들었다.
- 디스크 20GB 표기에 비해 루트 파티션이 19G인 이유로 **다른 파티션(`/boot`, `/boot/efi`)** 또는 **파일시스템 예약 블록**을 들었다.
- 실측 근거로 어떤 명령의 어떤 줄을 봤는지 적었다(`free -h`의 `Mem:` 줄, `df -h /`의 `/dev/vda1` 줄).

### 정답 예시

오퍼링 표기 2 core와 `nproc`·`lscpu`의 `CPU(s): 2`는 정확히 일치했다. 메모리는 표기가 4096MB인데 `free -h`의 total은 3.8Gi로 조금 작게 나왔고, 이는 커널과 펌웨어가 예약해 둔 영역이 total 계산에서 제외되기 때문이며 여기에 GB와 GiB의 단위 차이가 더해진 결과다. 디스크는 Root disk 기본 20GB인데 `df -h /`의 루트 파일시스템이 19G로 보이는데, `lsblk`를 보면 20G 디스크(`vda`) 안에서 루트 파티션(`vda1`) 외에 `/boot`·`/boot/efi` 같은 영역이 약 1G를 쓰고 있고 파일시스템 자체의 예약 블록도 있기 때문이다. 정리하면 CPU는 표기와 실측이 같고, 메모리와 디스크는 "표기는 할당량, 실측은 운영체제가 쓸 수 있는 양"이라는 차이 때문에 실측이 항상 조금 작다.

### 흔한 오답

- 콘솔의 `0.50 GHz` 표기와 실제 클럭을 비교하려 한다. 이 값은 오퍼링 정의값이고 물리 CPU의 클럭이 아니므로 비교 대상이 아니다.
- "메모리를 다른 프로세스가 쓰고 있어서 작게 나온다"고 쓴다. 쓰고 있는 양은 `used`와 `available`에 반영되고, 지금 문제는 `total` 자체가 작게 나오는 이유다. 두 열을 구분해야 한다.

## 4번

> 문제: **포트 목록의 변화 설명.** 4단계와 5-6단계의 `ss -tlnp` 출력을 나란히 붙이고, 무엇이 늘었으며 그 줄의 `Local Address`가 `0.0.0.0`(또는 `*`)인 것이 왜 중요한지 설명하라. 만약 `127.0.0.1:80`으로 열려 있었다면 6단계에서 무슨 일이 일어났을지도 함께 쓰라.

```
# 4단계 (웹서버 설치 전)
$ sudo ss -tlnp
State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
LISTEN 0      4096   0.0.0.0:22         0.0.0.0:*         users:(("sshd",pid=812,fd=3))
LISTEN 0      4096      [::]:22            [::]:*         users:(("sshd",pid=812,fd=4))

# 5-6단계 (apache2 설치 후)
$ sudo ss -tlnp
LISTEN 0      4096   0.0.0.0:22       0.0.0.0:*  users:(("sshd",pid=812,fd=3))
LISTEN 0      511          *:80             *:*  users:(("apache2",pid=1543,fd=4))
```

### 채점 기준

- 늘어난 것을 **포트 `80`, 프로세스 `apache2`** 로 정확히 지목했다. 두 출력을 나란히 붙였다.
- `0.0.0.0`(또는 `*`)의 의미를 "모든 인터페이스에서 요청을 받는다"로 설명하고, 그래서 루프백뿐 아니라 `ens3`의 사설 IP(`10.0.X.X`)로 오는 요청도 받는다는 점까지 연결했다.
- `127.0.0.1:80`이었다면 6단계에서 어떤 결과가 나오는지 구체적으로 썼다. `curl localhost`는 성공하지만 노트북에서 `curl http://10.0.X.X`는 **연결 거부(Connection refused)** 가 되고, `nc -vz 10.0.X.X 80`도 refused로 실패한다.
- refused와 timeout을 구분했다(가점). refused는 VM까지 닿았으나 받아 줄 대상이 없는 것이고, timeout은 내부망까지 못 들어간 것이다.

### 정답 예시

4단계에서는 `22`(sshd)만 `LISTEN`이었고, 5단계에서 apache2를 설치한 뒤에는 `*:80`이 `apache2` 프로세스 이름과 함께 새로 생겼다. 이 줄의 `Local Address`가 `0.0.0.0`(또는 `*`)이라는 것은 특정 주소가 아니라 이 서버가 가진 모든 인터페이스에서 요청을 받는다는 뜻이므로, 루프백(`127.0.0.1`)뿐 아니라 `ens3`의 사설 IP `10.0.X.X`로 들어오는 요청도 같은 프로세스가 받는다. 그래서 6단계에서 VPN에 연결된 내 노트북이 `http://10.0.X.X`로 바로 접속할 수 있었다. 만약 `127.0.0.1:80`으로만 열려 있었다면 VM 안에서 `curl -I localhost`는 `200 OK`로 성공하지만, 노트북에서의 `nc -vz 10.0.X.X 80`과 `curl http://10.0.X.X`는 연결 거부(Connection refused)로 실패했을 것이다. "서버 안에서는 되는데 밖에서는 안 되는" 대표적인 원인이 바로 이 Listen 주소 하나다.

### 흔한 오답

- `127.0.0.1:80`인 경우의 결과를 "방화벽에 막힌다"고 쓴다. 이번 주 기본 Shared Network에는 플랫폼 차원의 포트 통제 수단이 없고, 이 상황은 방화벽 문제가 아니라 프로세스가 그 주소에서 듣고 있지 않은 것이다. 증상도 다르다. 차단은 대개 timeout, 미수신은 refused다.
- `[::]:22` 줄이 사라진 것을 변화로 적는다. IPv6 대기 줄이며 이번 실습의 판단 대상이 아니다.

## 5번

> 문제: **네트워크 모델 비교.** 1주차 Isolated Network와 이번 주 기본 Shared Network에서, 내 노트북이 VM의 80번 포트에 닿기까지 거치는 구간을 각각 순서대로 쓰고, 각 구간의 통과 여부를 결정하는 설정 이름을 적으라. 그다음 **두 방식이 각각 무엇을 얻고 무엇을 포기했는지**를 2~3문장으로 서술하라. (6-2단계에서 다른 학생의 서버가 그대로 보였다는 사실을 근거로 쓸 수 있다)

**1주차 Isolated Network 경로**

| 순서 | 구간 | 통과 여부를 결정하는 설정 |
|---|---|---|
| 1 | 내 노트북 → 학교 VPN 터널 | VPN 프로파일·계정 (연결 상태) |
| 2 | VPN → 공용 IP | 그 네트워크에 배정된 Source NAT 공용 IP |
| 3 | 공용 IP → 통과 허용 | **방화벽 규칙** (Source CIDR `10.8.0.0/24`, TCP 포트 범위) |
| 4 | 공용 포트 → 사설 포트 변환 | **포트 포워딩 규칙** (공용 `8001` → 사설 `80`, 대상 VM) |
| 5 | 가상 라우터 → VM 사설 IP | 격리 네트워크의 내부 경로 |
| 6 | VM 내부 | 게스트 OS 방화벽(`ufw`) |
| 7 | 포트 80 수신 | apache2의 Listen 주소 (`0.0.0.0:80`) |

**2주차 기본 Shared Network 경로**

| 순서 | 구간 | 통과 여부를 결정하는 설정 |
|---|---|---|
| 1 | 내 노트북 → 학교 VPN 터널 | VPN 프로파일·계정 (연결 상태) |
| 2 | VPN → 내부망 `10.0.0.0/16` | 없음. VPN이 붙는 순간 내 노트북이 이 내부망 안에 들어간다 |
| 3 | 내부망 → VM 사설 IP `10.0.X.X` | 없음. 같은 `/16` 대역이므로 게이트웨이 `10.0.0.1`을 거치지도 않는다 |
| 4 | VM 내부 | 게스트 OS 방화벽(`ufw`). 이번 주 유일한 통제 지점이다 |
| 5 | 포트 80 수신 | apache2의 Listen 주소 (`0.0.0.0:80`) |

콘솔에서 만들 규칙이 이번 주에 하나도 없다는 점이 핵심이다. 포트포워딩·방화벽·Egress 규칙 없이 `http://10.0.X.X`로 바로 닿는다.

### 채점 기준

- 1주차 경로에 **포트 포워딩**과 **방화벽** 두 규칙이 둘 다 들어 있다. 하나만 쓰면 감점이다. 포워딩만으로는 들어오지 못한다.
- 2주차 경로에서 그 두 규칙이 **없다**고 명시했다. 있는 것처럼 쓰면 오답이다.
- 두 경로 모두 마지막에 게스트 OS 방화벽(`ufw`)과 Listen 주소가 남아 있다는 점을 적었다.
- 트레이드오프를 양방향으로 서술했다. Shared는 편의를 얻고 격리를 포기, Isolated는 경계 통제를 얻고 설정 부담·포트 번호 관례를 감수한다는 대칭이 있어야 한다.
- 6-2단계 사실(규칙을 만들지 않았는데 다른 학생의 서버가 보였다)을 근거로 인용하면 가점이다.

### 정답 예시

기본 Shared Network는 규칙을 하나도 만들지 않고 원래 포트 번호 `80` 그대로 접속되는 편의를 얻었지만, 그 대가로 격리를 포기했다. 이 네트워크는 `acltype=Domain`이고 제공 서비스가 `Dhcp`·`Dns`·`UserData`뿐이라 플랫폼 차원의 포트 통제 수단이 아예 없으며, 6-2단계에서 아무 설정도 하지 않은 상태로 옆자리 학생의 서버 페이지가 그대로 보인 것이 그 증거다. 반대로 1주차 Isolated Network는 공용 IP 앞에서 방화벽의 Source CIDR과 포트 포워딩으로 "누가 어느 포트로 들어올 수 있는가"를 내가 정하는 경계 통제를 얻었지만, 규칙을 직접 만들어야 하는 설정 부담과 공용 IP 하나를 여러 VM이 나눠 쓰기 때문에 생기는 포트 번호 관례(`8001`, `8002`)를 받아들여야 했다. 이번 주 구성에서 남은 방어선은 각 VM의 OS 방화벽(`ufw`) 하나뿐이며, 7주차에서 이 부분을 직접 좁힌다.

### 흔한 오답

- 2주차 경로에 "포트포워딩 `8001` → `80`"을 넣는다. 이번 주에는 그 규칙이 없다. 부록(선택 과제)에서만 다루는 내용이다.
- 게이트웨이 `10.0.0.1`을 반드시 거치는 구간으로 적는다. `ip route`의 `10.0.0.0/16 dev ens3 ... scope link` 줄이 있으므로 같은 대역 안의 통신은 게이트웨이를 거치지 않는다. 게이트웨이는 대역 밖으로 나갈 때의 문이다.
- "Shared Network는 보안이 없으니 나쁘다"로 끝낸다. 무엇을 얻었는지를 함께 써야 트레이드오프 서술이다.

## 6번

> 문제: **진단 순서 설계.** "브라우저에서 페이지가 안 열린다"는 신고를 받았다고 가정하고, 이 문서 6단계의 계층별 확인 표를 참고해 **확인 순서 여섯 단계**를 명령과 함께 쓰라. 각 단계에서 실패했을 때 원인이 어느 계층에 있는지도 한 줄씩 적으라.

### 채점 기준

- 순서가 **서버 안쪽에서 바깥쪽으로** 진행한다(서비스 → 포트 → 자기 응답 → 사설 IP 응답 → 노트북 연결 → 노트북 HTTP). 순서가 뒤섞이면 감점이다.
- 각 단계에 실제 명령이 붙어 있고, **어디에서 실행하는지**(내 VM인지 내 노트북인지)가 구분되어 있다.
- 실패 시 원인 계층이 단계마다 다르게 지목되어 있다. 여섯 줄이 모두 "네트워크 문제"면 의미가 없다.
- 이번 주 구성에서는 마지막 구간의 원인이 **VPN 연결과 호스트 방화벽 두 가지로 좁혀진다**는 점을 반영했다.

### 정답 예시

| 순서 | 어디에서 | 명령 | 실패하면 원인 계층 |
|---|---|---|---|
| 1 | 내 VM | `systemctl status apache2 --no-pager` | 서비스 계층. 프로세스 자체가 죽었다. `sudo systemctl start apache2` 후 `sudo journalctl -u apache2 -n 20`으로 이유를 본다 |
| 2 | 내 VM | `sudo ss -tlnp \| grep ':80'` | 서비스 설정 계층. 프로세스는 살았는데 포트를 열지 않았거나 Listen 주소가 `127.0.0.1`이다 |
| 3 | 내 VM | `curl -I localhost` | 웹 문서·권한 계층. 아직 네트워크는 무관하다. `404`면 파일이 없는 것이고 `403`이면 권한 문제다 |
| 4 | 내 VM | `curl -I http://10.0.X.X` | 게스트 OS 방화벽 계층. 3번은 되는데 여기가 안 되면 `sudo ufw status`를 본다 |
| 5 | 내 노트북 | `nc -vz 10.0.X.X 80` | 경로 계층. timeout이면 VPN 연결이나 VM 상태를 본다. refused면 다시 1~2번으로 돌아간다 |
| 6 | 내 노트북 | `curl -I http://10.0.X.X` | 클라이언트 계층. 1~5가 정상인데 브라우저만 안 열리면 캐시이거나 주소창에 `https://`가 자동으로 붙은 경우다. `http://`를 명시하고 강제 새로 고침을 한다 |

1번부터 4번까지 모두 성공하는데 5번이 실패하면 **서버는 정상이고 경로만 문제**라는 결론이 확정된다. 이번 주 구성에서 그 경로 문제는 사실상 VPN 연결 하나로 좁혀진다.

### 흔한 오답

- 브라우저 새로 고침이나 노트북의 `curl`부터 시작한다. 여기서 실패하면 원인이 서비스인지 포트인지 방화벽인지 경로인지 전혀 좁혀지지 않는다.
- 콘솔의 포트포워딩·방화벽 규칙 확인을 단계에 넣는다. 이번 주에는 그런 규칙이 없으므로 확인할 것이 없다.
- `ping 10.0.X.X`만으로 판정한다. ICMP가 통해도 80번 포트가 열렸다는 뜻은 아니다. 포트 도달성은 `nc -vz`로 본다.

## 7번

> 문제: **DNS와 연결의 구분.** `ping 8.8.8.8`은 성공하는데 `curl https://ubuntu.com`이 실패하는 상황을 가정하고, 원인을 좁히기 위해 실행할 명령을 순서대로 두 개 이상 제시하고 각 명령의 결과로 무엇을 알 수 있는지 서술하라.

### 채점 기준

- 첫 명령이 **이름 해석 확인**이다(`getent hosts ubuntu.com` 또는 `dig ubuntu.com`). IP로는 통하는데 이름으로 실패하는 상황이므로 여기서 갈린다.
- 이름 해석이 실패했을 때와 성공했을 때 **각각 다음에 무엇을 의심하는지** 갈래를 나눴다.
- 이름 해석 설정을 보는 명령(`resolvectl status`, `cat /etc/resolv.conf`)을 포함했다. `/etc/resolv.conf`의 `127.0.0.53`은 로컬 스텁 리졸버이고 실제 상위 네임서버는 `resolvectl status`의 `DNS Servers`에 나온다는 점을 구분하면 가점이다.
- 이름 대신 IP로 직접 접속해 보는 검증(`curl -I https://{IP}`)을 넣어 결론을 확정했다.

### 정답 예시

```
# 1. 이름 해석부터 확인한다
$ getent hosts ubuntu.com
(출력 없음, 종료 코드 2)

# 2. 어떤 네임서버를 쓰고 있는지 본다
$ cat /etc/resolv.conf
nameserver 127.0.0.53
options edns0 trust-ad

$ resolvectl status | head -20
Link 2 (ens3)
Current Scopes: DNS
     DNS Servers: 10.0.0.1

# 3. 이름 대신 IP로 붙여 본다
$ dig +short ubuntu.com @10.0.0.1
$ curl -I https://185.125.190.20
```

1번 `getent hosts ubuntu.com`이 아무것도 출력하지 않으면 이름이 IP로 변환되지 않은 것이므로, 원인이 연결이 아니라 이름 해석(DNS)임이 확정된다. 반대로 IP가 정상적으로 나왔다면 DNS는 정상이고 원인은 그보다 위 계층(HTTPS·TLS, 목적지 서버, 아웃바운드 경로)에 있으므로 `curl -v https://ubuntu.com`으로 어느 단계에서 멈추는지 본다.

2번 `resolvectl status`로는 실제로 질의를 보내는 상위 네임서버 주소를 알 수 있다. 이 환경에서는 `DNS Servers`가 `10.0.0.1`로, 기본 게이트웨이와 같은 주소다. 이 줄이 비어 있으면 이름 서버를 받지 못한 것이므로 DHCP 재요청이 필요하고, 주소가 있는데도 응답이 없으면 `dig ubuntu.com @10.0.0.1`로 그 서버 자체가 답하는지 확인한다.

3번에서 `curl -I https://185.125.190.20`처럼 IP로 직접 응답이 돌아오면, 경로와 아웃바운드는 살아 있고 이름 해석만 끊긴 것이므로 DNS 문제로 결론이 확정된다.

### 흔한 오답

- `ping ubuntu.com`으로 판정한다. 실패해도 원인이 DNS인지 목적지의 ICMP 차단인지 구분되지 않는다. 이름 해석만 떼어 보려면 `getent hosts`나 `dig`를 쓴다.
- `/etc/resolv.conf`의 `127.0.0.53`을 보고 "네임서버가 잘못 설정되었다"고 결론 낸다. 이것은 우분투의 정상 구성(로컬 스텁 리졸버)이며, 실제 상위 서버는 `resolvectl status`에서 확인한다.
- `ping 8.8.8.8`이 성공한 것을 "인터넷이 정상"의 증거로 삼는다. 반대 방향으로도 주의해야 한다. 이 환경에서 외부 `ping`은 경로 중간에서 ICMP가 막혀 실패할 수 있으므로, 인터넷 연결 여부는 `curl`로 판단한다.

## 8번

> 문제: **서버 유형 판단.** 이 VM에 인메모리 캐시(Redis)를 올려 대량의 데이터를 담으려 한다면, 오늘 확인한 네 값 중 어느 것이 먼저 한계에 부딪히는지 지목하고, 이론의 서버 유형 다섯 가지 중 어느 유형으로 바꿔야 하는지 근거와 함께 쓰라. (5주차 실습으로 이어진다)

### 채점 기준

- 먼저 한계에 부딪히는 값으로 **메모리(RAM)** 를 지목했다.
- 근거가 "인메모리 캐시는 데이터를 디스크가 아니라 RAM에 올린다"는 성질에서 나왔다. `free -h`의 `available` 값을 인용하면 가점이다.
- 디스크가 남아 있어도 도움이 되지 않는 이유를 설명했다(용량 문제가 아니라 데이터가 놓이는 위치의 문제다).
- 바꿔야 할 유형으로 **메모리 최적화(Memory)** 를 지목했다. 확인 명령이 `free -h`라는 대응까지 적으면 완결이다.

### 정답 예시

네 값 중 먼저 한계에 부딪히는 것은 **메모리**다. Redis는 데이터를 디스크가 아니라 RAM에 올려 두고 응답하는 인메모리 캐시이므로, 담으려는 데이터 총량이 `free -h`의 `available`(예시 환경에서 약 3.3Gi)을 넘어서는 순간부터 문제가 생긴다. 반면 루트 디스크는 여유가 16G 남아 있고 vCPU 2개도 캐시 조회 자체로는 쉽게 포화되지 않으므로, 디스크가 남아 있다는 사실은 이 상황에서 도움이 되지 않는다. 용량 부족이 아니라 데이터가 놓이는 위치가 RAM이라는 것이 원인이다. 따라서 이론의 다섯 유형 중 큰 RAM을 중점적으로 보는 **메모리 최적화(Memory)** 유형으로 바꿔야 하고, 판단 근거로 쓰는 명령은 `free -h`다. 이 플랫폼에서는 같은 vCPU 수를 유지하면서 메모리가 더 큰 오퍼링(Large 4/8192, XLarge 8/16384)으로 옮기는 것이 그 실행 방법이며, 계정 자원 한도(VM 16대 · CPU 16코어 · 메모리 32GB) 안에서 선택해야 한다.

### 흔한 오답

- 디스크를 지목한다. "대량의 데이터"라는 표현에 반응한 것인데, 인메모리 캐시의 데이터는 RAM에 놓인다. 디스크를 지목하려면 그 데이터를 파일로 저장하는 경우여야 한다.
- 유형을 "스토리지 최적화"로 답한다. 위와 같은 이유로 틀린다.
- CPU를 지목한다. 조회량이 극단적으로 많은 상황이라면 CPU도 병목이 될 수 있지만, 문제가 묻는 것은 "대량의 데이터를 담을 때 먼저 부딪히는 한계"이므로 메모리가 답이다.

5주차에서 Redis(7.0.15 계열)로 인메모리 캐시를 직접 올리며, 오늘 읽은 `free -h`와 `df -h` 값이 그 실습의 출발점이 된다. 캐시가 담을 수 있는 양의 상한을 정하는 설정(`maxmemory`)과 오늘 확인한 실측 메모리가 어떻게 연결되는지도 그때 다룬다.

## 참고

- 이 실습은 매주 새로 만들고 끝나면 정리(Destroy)하는 시나리오다. 다음 주에 같은 VM을 이어 쓴다고 가정한 답안은 전제가 틀렸다.
- 예시 IP `10.0.X.X`, 호스트명 `web01-{학번}`, 커널 `6.8.0-xx-generic`, apache2 `2.4.58` 계열은 문서용 표기다. 답안에는 본인 출력에 나온 값을 그대로 쓴다.
