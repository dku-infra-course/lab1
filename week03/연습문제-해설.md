# 3주차 연습문제 해설

제출용이 아니다. 스스로 풀고 대조하는 용도이며, 중간고사 출제 범위가 이 문제들에서 나온다.

전제 환경: 격리 네트워크 `192.168.0.0/24`, web01 `192.168.0.10`(MASTER, priority 110), web02 `192.168.0.11`(BACKUP, priority 100), VIP `192.168.0.100`, 인터페이스 `ens3`, `virtual_router_id 51`, `auth_pass 1234`, `advert_int 1`.

---

## 1번

> 문제: web01의 Keepalived를 중지한 뒤, web02의 로그(`syslog` 또는 `journalctl`)에서 `Entering MASTER STATE` 메시지와 `ip addr`의 VIP 이동을 캡처하여 제출하라. 이어서 web01을 복구했을 때 VIP가 되돌아오는(Failback) 로그도 함께 제출하라.

캡처 제출형이므로 문장으로 쓸 정답은 없다. 아래 항목이 화면에 보이면 통과다.

### 통과 체크리스트

- [ ] 장애 주입 전 상태: web01의 `ip addr show ens3` 에 VIP가 있고, web02에는 없다.
- [ ] 페일오버 로그: web02 로그에 `Entering MASTER STATE` 가 찍혀 있다. 이 문자열이 캡처에 보이지 않으면 통과가 아니다.
- [ ] VIP 이동: web02의 `ip addr show ens3` 출력에 `inet` 줄이 두 개이고, 그중 하나가 `192.168.0.100/32` 다.
- [ ] 서비스 전환: 같은 네트워크의 VM에서 `curl 192.168.0.100` 응답이 `<h1>Backup Server</h1>` 로 바뀐다.
- [ ] 페일백 로그: web01을 다시 기동한 뒤 web02 로그에 우선순위 비교 줄과 `Entering BACKUP STATE`, `removing VIPs.` 가 찍혀 있다.
- [ ] 페일백 확인: `curl 192.168.0.100` 응답이 다시 `<h1>Active Server</h1>` 로 돌아오고, VIP가 web01에 있다.
- [ ] 캡처마다 어느 노드의 화면인지 구분된다(프롬프트의 호스트명 또는 `hostname` 출력이 함께 보이면 된다).

### 명령 순서와 기대 출력

로그 창은 두 노드에서 각각 미리 띄워 둔다.

```bash
sudo journalctl -u keepalived -f
```

기동 시점의 web01 로그다.

```
Keepalived_vrrp[1235]: (VI_1) Entering MASTER STATE
Keepalived_vrrp[1235]: (VI_1) setting VIPs.
Keepalived_vrrp[1235]: Sending gratuitous ARP on ens3 for 192.168.0.100
```

기동 시점의 web02 로그다.

```
Keepalived_vrrp[1240]: (VI_1) Entering BACKUP STATE
```

web01에서 장애를 주입한다. 두 노드를 동시에 멈추면 VIP가 어디에도 없게 되므로 한 번에 한 노드만 멈춘다.

```bash
sudo systemctl stop keepalived.service
```

이때 web02 로그에서 아래가 보이면 통과다.

```
Keepalived_vrrp[1240]: (VI_1) Backup received priority 0 advertisement
Keepalived_vrrp[1240]: (VI_1) Entering MASTER STATE
Keepalived_vrrp[1240]: (VI_1) setting VIPs.
Keepalived_vrrp[1240]: Sending gratuitous ARP on ens3 for 192.168.0.100
```

web02에서 VIP와 응답을 확인한다.

```bash
ip addr show ens3
curl 192.168.0.100
```

```
    inet 192.168.0.11/24 brd 192.168.0.255 scope global ens3
       valid_lft forever preferred_lft forever
    inet 192.168.0.100/32 scope global ens3
       valid_lft forever preferred_lft forever
```

```
<h1>Backup Server</h1>
```

web01을 복구한다.

```bash
sudo systemctl start keepalived.service
```

web02 로그에서 아래가 보이면 페일백 통과다.

```
Keepalived_vrrp[1240]: (VI_1) Master received advert from 192.168.0.10 with higher priority 110, ours 100
Keepalived_vrrp[1240]: (VI_1) Entering BACKUP STATE
Keepalived_vrrp[1240]: (VI_1) removing VIPs.
```

```
<h1>Active Server</h1>
```

PID(대괄호 안의 숫자)와 앞의 시각 표기는 환경마다 다르다. Keepalived 버전에 따라 문구가 조금 달라질 수 있으므로, 반드시 확인해야 하는 문자열은 `Entering MASTER STATE` 다.

### 흔한 오답

- 내 PC에서 `curl 192.168.0.100` 을 실행해 멈춘 화면을 제출한다. VIP는 격리 네트워크의 사설 주소이고 VPN에서 `192.168.0.0/24` 로는 직접 라우팅되지 않는다. 같은 네트워크의 VM에서 실행한다.
- 브라우저로 VIP를 확인하려 한다. 포트포워딩 규칙은 특정 VM에 묶이므로 노드 사이를 옮겨 다니는 VIP를 따라가지 않는다.
- `/var/log/syslog` 가 없어서 로그를 찾지 못했다고 적는다. Ubuntu 24.04는 journald가 기본이므로 `sudo journalctl -u keepalived -f` 를 쓴다.
- web01 로그만 캡처한다. 승계가 일어났다는 증거는 web02 로그에 있다.
- 페일오버만 제출하고 페일백을 빼먹는다. 문제는 두 방향을 모두 요구한다.

## 2번

> 문제: 장애 주입을 비교하라. (a) MASTER의 Keepalived를 중단한 경우, (b) MASTER의 Apache만 중단한 경우, 각각 VIP가 이동하는지 관찰하고, 결과가 다른 이유를 "VRRP가 무엇을 감시하는가" 관점에서 3~4문장으로 서술하라. (b)에서도 VIP를 옮기려면 무엇이 필요한지 한 줄로 제시하라.

### 채점 기준

- (a)에서는 VIP가 web02로 이동하고, (b)에서는 VIP가 web01에 그대로 남는다는 관찰 결과를 각각 명시했다.
- 이유를 "기본 설정의 Keepalived는 노드의 VRRP 상태(광고 송수신)만 감시하고, Apache 같은 응용 프로세스의 생존은 감시 대상이 아니다"로 설명했다.
- (b)의 결과를 "VIP는 살아 있는데 그 VIP로 들어온 요청을 처리할 웹 서버가 없는 상태"로 짚었다.
- 해결책으로 `vrrp_script` + `track_script`(헬스체크) 추가를 제시했다.

### 관찰 절차

```bash
# (a) web01 에서 Keepalived 중단
sudo systemctl stop keepalived.service
# web02 에서 확인
ip addr show ens3
curl 192.168.0.100     # -> <h1>Backup Server</h1>

# web01 복구 후 (b) 진행
sudo systemctl start keepalived.service
sudo systemctl stop apache2
# web02 에서 확인
ip addr show ens3      # web02 에 VIP 가 올라오지 않는다
```

(b)에서 VIP는 web01에 계속 붙어 있고, web02 로그에는 아무 상태 전이도 남지 않는다.

### 정답 예시

(a) MASTER의 Keepalived를 중단하면 web02 로그에 `Entering MASTER STATE` 가 찍히고 VIP가 web02로 이동해 응답이 `Backup Server` 로 바뀐다. (b) MASTER의 Apache만 중단하면 VIP는 web01에 그대로 남고 web02는 계속 BACKUP 상태이며, 결과적으로 VIP는 살아 있으나 그 주소로 들어온 요청을 처리할 웹 서버가 없는 상태가 된다. 두 결과가 다른 이유는 기본 설정의 Keepalived가 감시하는 대상이 노드의 VRRP 상태, 즉 상대 노드로부터 광고(Advertisement)가 계속 들어오는지 여부뿐이기 때문이다. Apache가 죽어도 Keepalived 프로세스는 살아 있어 광고를 정상적으로 계속 보내므로, 백업 입장에서는 마스터가 멀쩡한 것으로 보여 전환 조건이 성립하지 않는다.

(b)에서도 VIP를 옮기려면: Apache 생존을 확인하는 `vrrp_script` 를 정의하고 `vrrp_instance` 에서 `track_script` 로 물려, 확인 실패 시 priority가 내려가 백업이 승계하게 만든다.

### 참고: 헬스체크를 붙이는 위치

실습 기본 설정에는 없는 부분이다. 구조만 보면 아래 형태이며, 확인 명령과 주기·가중치 값은 서비스 특성에 맞춰 정한다.

```
vrrp_script chk_apache {
    script "..."      # Apache 생존을 확인하는 명령
    interval ...      # 확인 주기(초)
    weight ...        # 확인 결과에 따라 priority 를 조정할 값
}

vrrp_instance VI_1 {
    ...
    track_script {
        chk_apache
    }
}
```

이 헬스체크는 노드가 마스터 자격을 유지할지를 판단하는 VRRP 계층의 확인이다. 4주차 로드밸런서가 백엔드를 분산 대상에서 빼기 위해 수행하는 헬스체크와는 다른 계층이므로 섞어 쓰지 않는다.

### 흔한 오답

- "Apache가 죽으면 VRRP 광고도 멈춘다"고 쓴다. 광고를 보내는 주체는 Keepalived 프로세스이므로 Apache 상태와 무관하다.
- (b)를 Keepalived의 버그나 설정 오류로 단정한다. 기본 동작이 그렇게 정의되어 있을 뿐이다.
- 해결책으로 "Apache를 다시 시작한다"만 적는다. 문제는 전환 조건을 어떻게 설계하는지를 묻는다.
- 해결책을 4주차 로드밸런서 헬스체크와 동일한 것으로 설명한다. 감시 주체와 목적이 다르다.

## 3번

> 문제: `advert_int` 를 1초에서 더 큰 값(예: 5초)으로 바꾸면 Failover 체감 시간이 어떻게 달라지는지 설명하고, 운영 환경에서 이 값을 정할 때의 트레이드오프(장애 감지 속도 vs. 오탐·네트워크 부하)를 서술하라.

### 채점 기준

- `advert_int` 가 마스터의 광고 송신 주기이고, 백업은 그 광고가 끊긴 것을 근거로 장애를 판단한다는 인과를 설명했다.
- 값을 키우면 백업이 마스터 다운을 확정하기까지 기다리는 시간이 비례해서 늘어나므로 체감 전환 시간(서비스 중단 구간)이 길어진다고 썼다.
- 트레이드오프를 양방향으로 다뤘다. 값을 줄이면 감지가 빨라지지만 일시적 지연이나 패킷 손실을 장애로 오판할 위험과 광고 트래픽·처리 부하가 늘고, 값을 키우면 오탐과 부하는 줄지만 중단 시간이 길어진다.
- 정상 종료와 강제 차단에서 이 값의 영향이 다르게 나타난다는 점을 구분했다.

### 정답 예시

`advert_int` 는 마스터가 자기 생존을 알리는 광고를 보내는 주기이고, 백업은 그 광고가 더 이상 들어오지 않는 것을 근거로 마스터 장애를 판단한다. VRRP 표준은 백업이 마스터 다운을 확정하는 대기 시간을 광고 주기의 약 3배로 정의하므로, 이 값을 1초에서 5초로 키우면 대기 시간도 그만큼 배로 늘어나 체감 전환 시간, 즉 서비스가 응답하지 않는 구간이 길어진다. 반대로 값을 지나치게 줄이면 감지는 빨라지지만 순간적인 네트워크 지연이나 패킷 한두 개의 손실을 장애로 오판해 불필요한 전환이 반복될 수 있고, 광고 패킷과 그 처리 부하도 함께 늘어난다. 따라서 운영에서는 서비스가 허용하는 중단 시간을 기준으로 삼되 해당 네트워크의 안정성을 함께 보고 정하며, 링크가 불안정한 구간에서는 값을 조금 키워 오탐을 줄이는 선택이 낫다.

### 정상 종료와 강제 차단의 차이

- `systemctl stop keepalived` 처럼 정상 종료하면 Keepalived가 우선순위 0 광고를 보내고 물러난다. 백업은 그 광고를 받는 즉시 승계하므로 `advert_int` 를 키워도 전환이 거의 지연되지 않는다. 로그에 남는 줄이 `Backup received priority 0 advertisement` 다.
- 강제 전원 차단처럼 광고가 예고 없이 끊기면 백업은 대기 시간이 지나야 승계한다. `advert_int` 의 영향은 이 경우에 드러난다. 로그에서 `Receive advertisement timeout` 을 확인한다.
- 실습 7단계는 정상 종료로 진행하므로 전환이 즉시 일어난다. 이 문항의 지연을 눈으로 보려면 강제 차단 쪽을 관찰해야 한다.

```bash
sudo journalctl -u keepalived -f
# 정상 종료: Backup received priority 0 advertisement -> Entering MASTER STATE
# 강제 차단: Receive advertisement timeout -> Entering MASTER STATE
```

값을 바꿀 때는 두 노드에 같이 적용한다. 한쪽만 바꾸면 서로 기대하는 광고 주기가 어긋난다.

### 흔한 오답

- "`advert_int` 를 키우면 페일오버가 되지 않는다"고 쓴다. 전환이 늦어질 뿐 동작 자체는 한다.
- 트레이드오프를 한쪽만 쓴다. 감지 속도만 언급하고 오탐·부하를 빼면 문제가 요구한 서술이 아니다.
- 값을 작게 할수록 무조건 좋다고 결론 낸다. 플래핑(전환이 반복되는 상태)과 부하 증가를 함께 봐야 한다.
- 정상 종료 실험만 하고 "값을 키워도 전환 속도가 똑같다"고 결론 낸다. 우선순위 0 광고 때문에 즉시 승계된 경우다.

## 4번

> 문제: CloudStack 격리 네트워크에서 기본(멀티캐스트) 설정이 동작하지 않을 수 있는 이유와, 유니캐스트(`unicast_src_ip`/`unicast_peer`) 설정으로 해결되는 원리를 VRRP 관점에서 설명하라.

### 채점 기준

- VRRP(RFC 3768, RFC 5798)가 광고를 멀티캐스트 주소 `224.0.0.18`, IP 프로토콜 번호 112로 보낸다는 사실을 근거로 들었다.
- `224.0.0.18` 이 IANA가 Local Network Control Block(`224.0.0.0/24`)으로 예약한 대역이라 라우터가 전달하지 않으며, 따라서 VRRP는 같은 L2 세그먼트 안에서만 성립한다고 설명했다. 이것이 표준상의 설계 제약이고 구현 결함이 아니라는 점을 구분했다.
- 가상 네트워크가 이 멀티캐스트를 필터링하면 광고가 상대에 닿지 않아 양쪽이 모두 MASTER가 되는 상태(split-brain)로 이어진다고 연결했다.
- 유니캐스트가 해결책이 되는 이유를 "멀티캐스트 그룹 대신 지정한 상대 IP로 직접 광고를 보내므로 L2 멀티캐스트 전달에 의존하지 않는다"로 설명했다.
- DKU Solid Cloud에서는 기본 설정으로 정상 동작함이 실측으로 확인됐고 유니캐스트는 다른 환경용 대안이라는 점을 밝혔다.

### 정답 예시

VRRP(RFC 3768, RFC 5798)는 생존 신호인 광고를 멀티캐스트 주소 `224.0.0.18`, IP 프로토콜 번호 112로 보낸다. 이 주소는 IANA가 Local Network Control Block(`224.0.0.0/24`)으로 예약한 대역이어서 라우터가 다른 세그먼트로 전달하지 않으며, 그래서 VRRP는 애초에 같은 L2 세그먼트 안에서만 성립하도록 설계되어 있다. 가상 네트워크가 이 링크로컬 멀티캐스트를 필터링하거나 인터페이스에 원래 할당되지 않은 보조 IP(VIP)를 허용하지 않으면, 상대의 광고가 도달하지 않아 두 노드가 서로를 보지 못하고 양쪽 모두 자신을 MASTER로 판단하는 상태(split-brain)가 된다. `unicast_src_ip` 와 `unicast_peer` 를 지정하면 Keepalived는 멀티캐스트 그룹을 쓰지 않고 상대 노드의 유니캐스트 IP로 광고를 직접 보내므로, 프로토콜과 상태 기계는 그대로인 채 L2 멀티캐스트 전달에 의존하지 않게 되어 문제가 해소된다. 다만 이 수업의 DKU Solid Cloud 격리 네트워크에서는 멀티캐스트 광고와 VIP, 페일오버, 페일백이 기본 설정으로 정상 동작함이 2026-08-27 실측으로 확인됐으므로 실습에서는 기본 설정을 쓰고, 유니캐스트는 멀티캐스트가 막힌 다른 환경을 위한 대안으로 이해한다.

### 확인 방법

각 노드에서 상대의 광고가 실제로 들어오는지 본다.

```bash
sudo tcpdump -ni ens3 vrrp
```

상대 IP에서 오는 패킷이 보이면 멀티캐스트가 전달되는 것이다. 자기 것만 보인다면 전달이 막힌 상태이거나 `virtual_router_id`(51)·`auth_pass`(1234)가 두 노드에서 어긋난 경우다. DKU 환경에서는 후자가 원인일 가능성이 높으므로 값의 오타를 먼저 확인한다.

```bash
grep -nE 'virtual_router_id|auth_pass|priority' /etc/keepalived/keepalived.conf
```

### 참고: 퍼블릭 클라우드에서의 상황

기본 VPC는 이 링크로컬 멀티캐스트를 전달하지 않으므로 기본 설정 VRRP가 동작하지 않는다. AWS의 Transit Gateway 멀티캐스트 도메인은 IGMP로 가입하거나 소스를 등록해서 라우팅되는 멀티캐스트 그룹을 다루는 기능이므로, 애초에 라우팅 대상이 아닌 `224.0.0.0/24` 링크로컬 트래픽에는 쓸 수 없다. 그래서 클라우드에서는 VRRP를 유니캐스트로 바꾸고, VIP 자리에는 보조 IP 재할당이나 관리형 로드밸런서 같은 그 플랫폼 고유 기능을 쓰는 구성이 일반적이다.

### 흔한 오답

- "CloudStack 격리 네트워크는 멀티캐스트가 막혀 있다"고 단정한다. 문제는 "동작하지 않을 수 있는 이유"를 묻고 있고, DKU 환경 실측 결과는 정상 동작이다.
- 유니캐스트로 바꾸면 VRRP가 아닌 다른 방식이 된다고 쓴다. 프로토콜과 우선순위 기반 마스터 선출은 그대로이고 광고를 전달하는 방식만 바뀐다.
- 노드 방화벽 이야기만 하고 `224.0.0.0/24` 링크로컬 예약이라는 근거를 쓰지 않는다. 방화벽(IP 프로토콜 112 차단)은 별개의 원인이며, 두 원인을 구분해서 써야 한다.
- 유니캐스트가 항상 더 나은 방식이라고 결론 낸다. 유니캐스트는 상대 노드를 설정에 일일이 나열해야 하므로 노드가 늘어나면 관리 부담이 커진다.
- 유니캐스트 설정에서 `unicast_src_ip` 와 `unicast_peer` 를 두 노드에 같은 값으로 적는다. 자기 IP와 상대 IP이므로 노드마다 서로 반대로 들어간다.

## 문항 사이의 연결

- 2번의 헬스체크(`vrrp_script` + `track_script`)는 "VIP가 살아 있는 것"과 "서비스가 살아 있는 것"이 다르다는 점을 드러낸다. 3주차는 가용성 중심의 Active/Backup이고, 4주차 로드밸런싱은 성능 중심으로 두 대를 항상 같이 쓴다는 점에서 대비된다.
- 3번의 정상 종료와 강제 차단 차이는 1번 캡처에서 어떤 로그 줄이 나오는지를 결정한다. 실습 절차대로 `systemctl stop` 을 쓰면 우선순위 0 광고 줄이 먼저 보인다.
- 4번의 L2 제약은 이 실습이 왜 격리 네트워크를 새로 만들고 VM 두 대를 같은 `/24` 에 두는지에 대한 이유이기도 하다.
